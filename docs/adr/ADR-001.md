# ADR-001 — Persistência em PostgreSQL no Docker Compose, com SQL direto (psycopg)

- **Status:** aceita (revisada em 13/11/2026 — veja "Histórico")
- **Data:** 13/11/2026
- **Requisitos relacionados:** RF01, RF02, RF03, RF06, RF08, ASR01, ASR03

## Contexto

O protótipo precisa guardar os dados de forma persistente (seção 7 do enunciado). Até esta decisão, os chamados ficavam só na memória (`RepositorioEmMemoria`) e sumiam quando o servidor parava.

Três requisitos dependem diretamente de como os dados são gravados:

- **ASR01 (auditoria):** cada alteração gera um `RegistroAuditoria`, e o histórico nunca pode ser sobrescrito.
- **ASR03 (notificações):** a notificação pendente precisa sobreviver a uma queda ou reinício do servidor, para ser reenviada depois.
- **RF02, RF03 e RF06:** consultas com filtros combinados (equipamento, prioridade, técnico, estado, datas, solicitante, departamento) e o histórico por equipamento.

Além disso, a abertura de um chamado grava três coisas ao mesmo tempo (chamado, auditoria e notificação). Ou as três ficam salvas, ou nenhuma.

O sistema é um **monólito**: um único programa Python com todas as camadas. Mesmo assim, ele depende de dois serviços externos que rodam como programas separados: o banco de dados e o servidor de e-mail (RF08, que no ambiente local é o Mailpit).

A Aplicação já acessa os dados apenas pela interface `ManutencaoRepositorio`. Por isso, a escolha do banco afeta só a camada de Infraestrutura e o `main.py`.

## Problema e forças

- **Transações:** a gravação de chamado, auditoria e notificação precisa ser atômica (tudo ou nada).
- **Integridade:** os dados devem respeitar as regras mesmo se alguém acessar o banco sem passar pela aplicação (estados válidos, chaves estrangeiras, auditoria imutável).
- **Mesmo ambiente para todos:** cada um dos três integrantes roda o projeto no próprio computador, com sistemas diferentes. A professora também precisa conseguir rodar o protótipo.
- **Subir tudo junto:** a aplicação, o banco e o servidor de e-mail precisam estar no ar ao mesmo tempo para a demonstração.
- **Simplicidade:** o enunciado pede para evitar complexidade que os requisitos não justificam.
- **Testabilidade:** os testes do dia a dia devem rodar rápido e sem banco.
- **Coerência com o projeto:** a tecnologia definida pelo grupo em `organizacao.md` é PostgreSQL.

## Alternativas consideradas

### Onde guardar os dados e como rodar os serviços

| Alternativa | Vantagens | Desvantagens |
|---|---|---|
| **A. Só memória** (`RepositorioEmMemoria`) | Nada para instalar | Não atende à persistência exigida; perde notificações pendentes ao reiniciar (fere o ASR03) |
| **B. SQLite** | Nada para instalar (vem com o Python); o banco é um arquivo | Diferente da tecnologia definida pelo grupo; menos recursos de integridade e de concorrência que um servidor de banco |
| **C. PostgreSQL e Mailpit instalados em cada computador** | Inicia junto com o sistema operacional, sem esperar contêineres | Cada integrante instala e configura dois programas; os passos e as versões mudam conforme o sistema operacional |
| **D. PostgreSQL, Mailpit e a aplicação no Docker Compose** | Um comando sobe tudo; mesmas versões para todos; o banco já nasce com as tabelas e os dados de exemplo | Exige Docker instalado; a primeira execução baixa as imagens, e o Docker Desktop demora para iniciar em alguns sistemas |

### Como o Python acessa o banco

| Alternativa | Vantagens | Desvantagens |
|---|---|---|
| **E. ORM (SQLAlchemy)** | Menos SQL escrito à mão; mapeamento automático | Um segundo conjunto de classes (modelos do banco) além das classes do domínio; mais conceitos para o grupo aprender |
| **F. SQL direto com psycopg 3** | SQL visível e simples; nenhuma classe extra; todo o SQL fica em uma única classe | Conversão entre linhas e objetos escrita à mão |

## Decisão

Usar **PostgreSQL no Docker Compose (D)**, acessado com **SQL direto pelo psycopg 3 (F)**.

**Ambiente (`docker-compose.yml`):**

- **Três serviços sobem com um comando** (`docker compose up --build`):
  - `app`: a aplicação, ou seja, o monólito, com a imagem do `Dockerfile`;
  - `db`: PostgreSQL 18.7;
  - `mailpit`: o servidor de e-mail local.
- **O banco nasce pronto.** Na primeira execução, o contêiner `db` roda `banco/schema.sql` e `banco/dados_exemplo.sql`, e cria também o banco de testes (`banco/criar_banco_teste.sql`). Os dados ficam em um volume e continuam salvos entre uma execução e outra.
- **Versões fixas:** `postgres:18.7`, `axllent/mailpit:v1.33.1` e `python:3.12-slim` com as bibliotecas travadas pelo `uv.lock`.
- **As portas só aceitam conexões do próprio computador** (`127.0.0.1`). As senhas do `docker-compose.yml` servem apenas para desenvolvimento local.

**Acesso aos dados:**

- **`PostgresManutencaoRepositorio`** (Infraestrutura) implementa a interface `ManutencaoRepositorio`, a mesma do `RepositorioEmMemoria`. Todo o SQL do sistema fica nessa classe.
- **`salvar_chamado()`** grava chamado, técnicos, auditoria e notificação em **uma única transação**.
- **`banco/schema.sql`** cria as 7 tabelas: `departamento`, `usuario`, `equipamento`, `chamado`, `chamado_tecnico`, `registro_auditoria` e `notificacao`.
- **Regras garantidas pelo próprio banco:**
  - `CHECK` nos valores de estado, prioridade, papel e status;
  - chaves estrangeiras entre as tabelas;
  - um **gatilho** (*trigger*) que recusa `UPDATE` e `DELETE` em `registro_auditoria` (ASR01).
- **A tabela `notificacao` é a fila de e-mails** (ASR03): o `AgendadorNotificacoes` lê as linhas `PENDENTE`.

**Configuração e testes:**

- **O `main.py` escolhe as implementações pelas variáveis `DATABASE_URL` e `SMTP_HOST`.** O `docker-compose.yml` define essas variáveis para o contêiner `app`; fora do Docker, elas vêm do arquivo `.env`, que não vai para o git. Sem elas, o sistema usa o `RepositorioEmMemoria` e o `NotificadorFake`.
- **Os testes de unidade continuam usando o `RepositorioEmMemoria`.** Os testes do PostgreSQL rodam contra o banco `manutencao_teste` do contêiner, quando `TEST_DATABASE_URL` está definida.

## Consequências positivas

- **Atende ao ASR01 e ao ASR03:** as transações garantem tudo ou nada, e a auditoria não pode ser alterada nem por SQL direto.
- **Persistência real:** os dados e a fila de e-mails sobrevivem ao reinício da aplicação.
- **Um comando sobe tudo:** aplicação, banco e e-mail iniciam juntos, na ordem certa. O `app` espera o banco estar pronto, o que facilita a demonstração e a avaliação.
- **Mesmo ambiente para todos:** as mesmas versões rodam em qualquer sistema com Docker. Não é preciso instalar nem configurar PostgreSQL ou Mailpit.
- **Domínio, Aplicação e Apresentação não mudaram:** trocar a memória pelo PostgreSQL alterou só a Infraestrutura e o `main.py`. Isso mostra, na prática, a inversão de dependência que a arquitetura propõe.
- **Continua sendo um monólito:** o Docker muda como os programas são instalados e iniciados, não a arquitetura. A aplicação segue sendo um único programa.
- **Menos classes:** não há modelos de ORM; o SQL fica visível e fácil de explicar.
- **Testes rápidos:** os testes de unidade rodam sem banco e sem Docker.

## Consequências negativas, custos e riscos

- **Depende do Docker:** cada integrante precisa instalar o Docker. A primeira execução baixa as imagens, e o Docker Desktop pode demorar para iniciar.
- **Mudanças no código exigem reconstruir a imagem** (`docker compose up --build`). Para desenvolver com recarga automática, a API pode rodar fora do Docker (`uv run fastapi dev`), com o banco e o Mailpit no Docker.
- **Mapeamento escrito à mão:** é preciso converter linhas em objetos (`Chamado`, `Usuario`, ...). Isso gera mais código e várias consultas pequenas por chamado. É aceitável no volume do protótipo, mas precisaria de otimização com muitos dados.
- **Duas implementações para manter:** memória e PostgreSQL precisam se comportar igual. Os testes dos dois repositórios reduzem esse risco.
- **Sem migrações:** os scripts de `banco/` só rodam quando o volume é criado. Para mudar as tabelas, é preciso apagar os dados (`docker compose down -v`). Para evoluir o banco sem perder dados, seria preciso uma ferramenta de migração (por exemplo, Alembic).
- **Senhas fixas no `docker-compose.yml`:** são aceitáveis só em desenvolvimento local, com as portas restritas ao próprio computador. Em produção, elas precisariam vir de um gerenciador de segredos.

## Histórico

A primeira versão desta decisão escolheu a alternativa C: PostgreSQL instalado em cada computador, sem Docker, porque o grupo considerou o Docker lento para iniciar.

Ela foi revista no mesmo dia por dois motivos:

- instalar e configurar o PostgreSQL e o Mailpit em cada sistema operacional se mostrou trabalhoso;
- o grupo quis subir aplicação, banco e e-mail com um único comando.

A troca afetou só a forma de rodar o ambiente (`docker-compose.yml`, `Dockerfile`, `.env.example`). O código das camadas não mudou.

## Relação com a análise de evolução

Na troca **"PostgreSQL → outro mecanismo de persistência"** (seção 9 do enunciado):

- **Seria afetado:** só a Infraestrutura (uma nova classe que implemente `ManutencaoRepositorio`), o `main.py` e o serviço `db` do `docker-compose.yml`.
- **Ficaria igual:** Domínio, Aplicação e Apresentação.

O próprio protótipo já mostra essa troca: com ou sem `DATABASE_URL`, o mesmo service funciona com memória ou com PostgreSQL.
